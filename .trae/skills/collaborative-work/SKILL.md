# 协同工作模式（collaborative-work）

## 触发条件

用户消息以 **「协同工作」** 开头（如 `协同工作 让鱼在受惊时加速逃离`）时立即进入本模式。
「协同工作」之后的内容即为本次要处理的问题；若问题为空，先反问用户要处理什么。

## 核心规则（不可违反）

1. **只读**。本模式内唯一允许的写操作是：在 `e:\unity_git_manager\Yongxian\.trae\temp\` 下生成/更新一份临时记录 .md。
2. **禁止修改任何脚本或资产**。确认前不得对 `Assets/` 下任何文件执行写入、编辑、新建、删除。
3. **禁止驱动 Unity 编辑器**。不运行 `unity` CLI 命令、不执行 `unity command eval`、不进入 Play 模式、不触发重新编译或资产刷新。
4. **用户正在旁边同时操作 Unity 编辑器**。全程不得做任何会打断编辑器的动作（不写 Assets 下的文件、不占用/锁定工程文件）。
5. 允许且鼓励：读取文件、搜索代码、查阅引用关系——用于把修改方案写准确。

## 执行流程

### 第 1 步：只读分析

读取与问题相关的脚本/文件，确定：
- 涉及哪些文件
- 每处要改什么、为什么

### 第 2 步：生成临时记录

路径规则：`e:\unity_git_manager\Yongxian\.trae\temp\协同工作_<YYYYMMDD-HHmm>_<主题简述>.md`

记录模板：

```markdown
# 协同工作记录：<主题>

- 状态：待确认
- 创建时间：<yyyy-MM-dd HH:mm>
- 用户问题：<用户原文>

## 涉及文件

| 文件 | 修改点 | 说明 |
| --- | --- | --- |
| Assets/Scripts/Xxx.cs | 第 N 行的某逻辑 | 为什么改 |

## 修改方案

### 1. <文件> — <修改点>

- 现状：<现在是什么样，引用关键代码/行号>
- 改为：<改成什么样，给出目标代码>

### 2. ...

## 备注

- <风险、副作用、需要用户在编辑器里手动配合的事项（如挂载组件、改参数）>
```

若分析后认为**无需修改**，同样生成记录，在「修改方案」中写明「无需修改」及原因，然后进入第 3 步等待确认。

### 第 3 步：等待用户提交（关键）

- 用一句话告知：记录已生成、**尚未改动任何脚本**，并附记录文件的 `computer://` 链接。
- 然后**停止动作**，不执行任何脚本修改，等待用户回复。
- 用户给出修改意见时：只更新记录 .md，再次回到本步等待。

### 第 4 步：执行修改（仅限用户确认后）

用户回复「提交修改」「确认」「执行」「同意」等明确确认后，才按记录逐条修改脚本。

- 严格按记录执行；若执行中发现必须偏离记录，先停下更新记录并说明，再继续。
- 顺序建议：先改被依赖的脚本，再改依赖方，避免中间态编译错误。

### 第 5 步：收尾

- 修改完成后，把记录 .md 的「状态」改为 `已应用`，并补充实际改动与记录的差异（若无差异写「与记录一致」）。
- **保留记录文件，不删除**；同时把当次改动的文件清单与结论回给用户。

## 增强提示

- 记录中的文件路径用工作区相对路径（如 `Yongxian/Assets/Scripts/ConstantSpeedMover.cs`），行号以分析时的实际内容为准。
- 一次「协同工作」只对应一份记录文件；同一问题反复迭代时更新同一份，不新建。
- 若用户在等待期间说「取消」，把记录状态改为 `已取消` 并停止，不改任何脚本。
